# 电台连接和连续播放改进建议

2026-10-30，设计建议，尚未在 RC4 实现。

## 目前已知

此前 COM6 日志确有连续 15 秒没收到数据、停止音频并重连成功的记录；没有抓到所有卡顿的完整过程，不能直接把问题归因于某一个环节。此前电脑读取两条杭州 MP3 流首批 2KB 分别约 7.8 秒、1.7 秒，只能说明那次请求差异明显，不能当作当前设备网络指标。

HTTP 连接完成不意味着源站会一直按音频码率供数。需要区分 DNS/TCP/TLS、响应头、首字节、首个可解码帧、网络缓冲和 I2S 写入。官方接口阶段见 [ESP-IDF 5.5.3 HTTP Client](https://docs.espressif.com/projects/esp-idf/en/v5.5.3/esp32s3/api-reference/protocols/esp_http_client.html)。

当前源码已调用 WIFI_PS_NONE。环形缓冲为 64KiB、起播门槛 8KiB：按 128kbps 估计分别约 4.1 秒、0.5 秒。码率越高，可承受的空档越短；缓冲区有容量也不代表开播时就已装满。

## 推荐顺序

1. 先补测量。记录各 URL 的连接、首帧时间、码率、有效字节速率、最低缓冲余量、断粮次数和音频写入错误。只在状态变化或会话结束输出摘要，避免逐帧串口日志。
2. 做稳播模式。PSRAM 压缩音频缓冲可先尝试 256KiB，按估计码率攒约 2–3 秒再开播；发生断粮时进入明确 BUFFERING 状态，攒够目标余量后一次恢复。先验证较少中断，再逐步减小健康源起播等待。256KiB 在 128kbps 下约 16.4 秒容量，不等于每次开播都要等 16 秒。
3. 源质量优选。统计首帧时间、失败和断流，稳定源优先，失败源临时冷却；有同台备用源时优先换源。不要把 HTTP 200 当成“可持续播放”，要检验实际可解码帧。
4. 有限重试与清楚反馈。允许用户在连接和缓冲期间直接换台；显示失败后可重试。自动跳到下一台应作为明确可选策略，避免用户点了一台却听到另一台。
5. 若同一台在手机热点与家中 Wi-Fi 下明显不同，再检查本地无线链路；若仅个别 URL 长期卡顿，则优先换源。若所有源都卡而缓冲余量充足，再查解码耗时和 I2S 输出，避免无证据修改平台时序。

扩大缓冲能吸收短时抖动，无法修复长期低于播放码率的供数或源站持续断流。单纯增大 HTTP timeout 也不能提高下载速度，只会推迟失败反馈。大规模不稳定时可另行评估统一转发服务，但会增加服务器与维护成本。
